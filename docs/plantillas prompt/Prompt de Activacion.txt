## REGLAS DE UI / DISEÑO (CRÍTICAS)

Siempre que se cree o modifique UI:

OBLIGATORIO consultar el libro de estilo.

También es OBLIGATORIO consultar las skills disponibles, leer completamente las
instrucciones de las aplicables y declarar cuáles se usarán y en qué orden.

### Enrutamiento automático de skills frontend

- Usar siempre `impeccable`, `ui-ux-pro-max` y `emil-design-eng` como núcleo
  cuando la TASK incluya diseño, rediseño, implementación o mejora visual.
- Usar `review-animations` para revisar animaciones concretas existentes.
- Usar `improve-animations` para auditar el motion general y producir planes, y
  `find-animation-opportunities` para encontrar oportunidades; ambas son de
  solo lectura y no deben presentarse como implementación.
- Usar `apple-design` para gestos, springs, drag/swipe, sheets, momentum,
  profundidad, materiales translúcidos o reduced-motion.
- Usar `animation-vocabulary` solamente para identificar el nombre preciso de
  un efecto descrito de forma vaga.
- Invocar `prototype` si el objetivo pide explorar variantes de una pieza UI e
  invocar `pick-ui-library` si requiere escoger una librería; ambas necesitan
  invocación expresa.
- El libro de estilo, los componentes existentes, las licencias, la TASK activa
  y las guardas Clásico/BIM tienen precedencia sobre cualquier recomendación.
- Ninguna skill autoriza features, dependencias o refactors fuera del slice.
- Validar el resultado real: las skills no sustituyen build, smoke, QA visual,
  accesibilidad ni comprobación de licencias y no interferencia BIM.

## REGLA CRÍTICA DE SINCRONIZACIÓN DOCUMENTAL

OBLIGATORIO antes de ejecutar, continuar o cerrar cualquier TASK:

1. Confirmar que la TASK activa real coincide en:
   - docs/runtime/WORK_MODE_STATE.json
   - TODO.md
   - docs/HANDOFF.md
   - docs/project_state.json
   - docs/CHANGELOG.md
   - docs/tasks/TASK-XXXX.md

2. Si existe contradicción documental:
   - detener la ejecución funcional
   - declarar explícitamente la contradicción
   - sanear primero la documentación
   - no implementar código hasta que la TASK activa quede alineada

3. Si una TASK aparece como activa pero ya tiene implementación, validación y cierre:
   - marcarla como completada o histórica
   - actualizar WORK_MODE_STATE
   - actualizar HANDOFF
   - actualizar project_state
   - registrar el saneamiento en CHANGELOG

4. Si una TASK nueva o distinta pasa a ser la activa:
   - actualizar docs/runtime/WORK_MODE_STATE.json
   - actualizar TODO.md con el pendiente real
   - actualizar docs/HANDOFF.md
   - dejar trazabilidad en docs/CHANGELOG.md

5. Nunca confiar en una sola fuente documental.
   La TASK activa real debe inferirse por consenso entre runtime, TODO, TASK, CHANGELOG y estado operativo.

6. No se puede cerrar una sesión con:
   - WORK_MODE_STATE apuntando a una TASK cerrada
   - HANDOFF diciendo "sin TASK abierta" si existe pendiente real
   - TODO contradiciendo la TASK activa
   - CHANGELOG sin registrar el cambio ejecutado
   - project_state desactualizado si cambió el estado rector del proyecto

   - avance anterior

## REGLA CRÍTICA DE VALIDACIÓN REAL OBLIGATORIA

OBLIGATORIO antes de declarar solucionado cualquier bug, regresión, hotfix, slice funcional o ajuste de datos:

1. No basta con compilar.
   - `build`, `lint`, `smoke` o pruebas estáticas solo confirman integridad técnica mínima.
   - Nunca declarar un problema funcional como resuelto solo porque compila.

2. Confirmar el resultado real del flujo afectado.
   - Verificar el dato, endpoint, estado de UI o comportamiento exacto que originó el problema.
   - Si el bug afecta datos visibles, comprobar el caso concreto con datos reales o una reproducción equivalente.
   - Si el bug afecta una llamada API, comprobar el contrato real de entrada/salida.
   - Si el bug afecta UI, confirmar que la UI consume el dato corregido y no una caché, fallback o estado anterior.

3. La validación debe responder explícitamente:
   - qué fallaba
   - qué se cambió
   - qué caso real se comprobó
   - qué resultado exacto se obtuvo
   - qué pruebas técnicas acompañan la comprobación

4. Si no es posible validar en UI real/desplegada:
   - declarar la limitación explícitamente
   - no cerrar al 100%
   - dejar pendiente QA visual/desplegada
   - documentar qué evidencia sí fue obtenida

5. Prohibido sustituir validación funcional por mensajes de error, placeholders o avisos al usuario.
   - Si el usuario reporta que un dato no carga, la solución debe recuperar el dato o corregir la fuente.
   - Mostrar que falló solo es diagnóstico, no solución.

6. Esta regla es de cumplimiento obligatorio.
   - Si entra en conflicto con prisa, coste de tokens o cierre documental, prevalece la validación real.
   - No volver a cerrar ni afirmar una corrección sin evidencia funcional concreta.
