# TASK-0322 - Comunidad: precondiciones funcionales antes de implementación

## Estado
COMPLETED

## Objetivo
Cerrar las decisiones funcionales críticas del módulo `Comunidad` antes de empezar a codificar, para no reabrir después modelo de datos, permisos, contratos o UI.

## Decisiones a resolver

### 1. Reacciones y adjuntos
- Si habrá `like` o reacciones desde fase 1
- Si las publicaciones aceptarán:
  - imágenes
  - documentos
  - otros adjuntos
- Si los mensajes directos aceptarán adjuntos
- Regla fijada:
  - `Público`: no admite archivos ni links; solo imágenes
  - `Interno empresa`: admite archivos
  - retención obligatoria de archivos internos: `30 días`
  - al superar `30 días`, el archivo debe eliminarse automáticamente

### 2. Estados de publicación
- Si una publicación puede pasar por:
  - borrador
  - publicada
  - oculta
  - cerrada
  - archivada
- Si existirán publicaciones:
  - fijadas
  - destacadas

### 3. Moderación operativa
- Si los usuarios podrán denunciar publicaciones o respuestas
- Si existirá cola de revisión
- Si los administradores usarán:
  - ocultación temporal
  - cierre de hilo
  - borrado lógico o físico
- Si habrá bitácora de moderación visible para administradores

### 4. Mensajería directa
- Si será solo `1 a 1` o también grupos
- Si tendrá estados:
  - enviado
  - leído
  - bloqueado
- Si permitirá adjuntos
- Si habrá retención o histórico ilimitado

### 5. Notificaciones
- Si habrá contador interno
- Qué eventos generan notificación:
  - respuesta
  - mención
  - mensaje directo
  - sanción
  - moderación sobre el contenido propio

### 6. Búsqueda y filtros
- Si la búsqueda cubrirá:
  - texto
  - autor
  - ámbito
  - fecha
- Qué filtros mínimos existirán en fase 1

### 7. Perfil comunitario
- Qué atributos se muestran:
  - nombre
  - empresa
  - cargo
  - avatar
  - bio corta

### 8. Auditoría y cumplimiento
- Qué acciones administrativas deben quedar auditadas
- Si habrá acceso excepcional a DM y bajo qué regla
- Qué eventos sensibles se registrarán obligatoriamente

### 9. Límites y anti-spam
- longitud máxima de publicaciones
- longitud máxima de mensajes directos
- límite de frecuencia
- tamaño y tipo de adjuntos

### 10. Datos de prueba y semilla
- Si se sembrarán ejemplos para:
  - público
  - interno empresa
  - DM

### 11. Ámbito exacto del foro público
- Si el área pública será visible:
  - solo para usuarios autenticados

### 12. Respuestas y profundidad jerárquica
- Si las respuestas serán:
  - planas
  - anidadas

### 13. Edición y borrado por autor
- Si el autor puede:
  - editar su propia publicación
  - borrar su propia publicación
- Durante cuánto tiempo
- Qué restricciones aplican si el contenido ya tiene respuestas

### 14. Cierre de publicaciones
- Quién puede cerrar un hilo
- Si un hilo cerrado:
  - sigue visible
  - deja de aceptar respuestas

### 15. Visibilidad de perfil comunitario
- Qué atributos del usuario se exponen en Comunidad:
  - nombre
  - empresa
  - cargo
  - avatar
- Si algún dato puede ocultarse

### 16. Bloqueos entre usuarios en DM
- Si un usuario puede bloquear a otro directamente
- Cómo afecta eso a:
  - mensajes nuevos
  - respuestas
  - historial

### 17. Menciones
- Si existirá `@usuario`
- Si puede mencionar:

### 18. Etiquetas o categorías temáticas
- Si el foro público e interno tendrán tags/categorías desde fase 1
- O si se posterga para evitar complejidad inicial

### 19. Borrado lógico vs. físico
- Si publicaciones, respuestas y DM usan:
  - soft delete
  - delete físico
- Qué datos deben conservarse por auditoría

### 20. Orden del feed
- Si el foro ordena por:
  - creación
  - actividad reciente
  - fijados + actividad

### 21. Adjuntos y almacenamiento
- Dónde se almacenarán adjuntos de:
  - publicaciones
  - respuestas
  - mensajes directos
- Qué tipos se permiten
- Qué tamaño máximo tendrán
- Si el tratamiento será común o distinto entre foro y DM
- Regla fijada:
  - el tratamiento no es común entre `Público` e `Interno`
  - `Público` solo permite imágenes
  - `Público` no permite compartir archivos ni links
  - `Interno empresa` permite archivos con caducidad automática a `30 días`

### 22. Retención y conservación
- Cuánto tiempo se conservarán:
  - mensajes borrados lógicamente
  - publicaciones ocultas o moderadas
  - auditorías de acceso y sanción
- Si habrá purga manual, automática o ninguna en fase 1
- Regla fijada:
  - los archivos adjuntos del área interna deben eliminarse automáticamente tras `30 días`
  - esta purga debe ser automática, no depender de borrado manual

### 23. Rate limiting y anti-spam operativo
- Cuántas publicaciones por ventana de tiempo
- Cuántas respuestas por ventana de tiempo
- Cuántos DM por ventana de tiempo
- Qué sanción operativa se aplica al exceso:
  - bloqueo temporal
  - advertencia
  - cola manual

### 24. Denuncia y apelación
- Si el usuario podrá denunciar:
  - publicaciones
  - respuestas
  - mensajes directos
- Si existirá:
  - cola de revisión
  - estado de denuncia
  - apelación de sanción o moderación

### 28. Infracciones automáticas por reglas del sistema
- Debe existir política automática de sanción por intento de publicar links en `Público`
- La escalada queda fijada:
  - 1ra: `7 días`
  - 2da: `15 días`
  - 3ra+: baneo completo de `Comunidad`
- La infracción debe generar:
  - evento persistente
  - aviso al `superadmin`
  - datos mínimos: usuario, fecha, ámbito, extracto y sanción aplicada

### 29. Estado de usuarios comunitarios
- `Superadmin` debe poder ver:
  - usuarios comunitarios
  - estado actual en Comunidad
  - sanciones activas
  - última conexión
- La última conexión se resuelve con `last_active_at`

### 30. Rol especializado de Comunidad
- Se añade el rol `usuario_comunidad`
- Debe quedar restringido a:
  - acceso directo a `Comunidad`
  - lectura/publicación según permisos de tema
  - sin acceso al resto de módulos

### 31. Temas y membresía por tema
- Los temas deben poder restringir acceso por usuario
- `Superadmin` administra cualquier tema
- `Administrador de empresa` administra temas internos de su empresa
- Los usuarios solo pueden ver/publicar en temas para los que estén habilitados o que sean abiertos

- búsqueda básica
- auditoría base
- soft delete

### Fase 2

- tags/categorías temáticas avanzadas
- presencia/estado en línea
- exportaciones
- apelaciones complejas
- analítica avanzada
- automatizaciones y reglas de escalado

## 26. Matriz final de permisos

### Usuario estándar
- ver `Público`
- ver `Interno` de su empresa activa
- publicar/responder según ámbito permitido
- editar/borrar su contenido dentro de la política definida
- usar DM dentro de la política permitida
- no moderar
- no sancionar

### Administrador de empresa
- todo lo anterior dentro de su empresa
- moderar contenido del foro interno de su empresa
- aplicar sanciones comunitarias internas de su empresa
- no moderar globalmente `Público`
- no expulsar del sistema

### Superadministrador
- ver y moderar todo el foro
- sancionar globalmente `Comunidad`
- acceso administrativo excepcional auditado cuando aplique
- no tratar `Comunidad` como sustituto de expulsión total del sistema

## 27. Criterios de aceptación mínimos
- un usuario normal ve solo `Público` + interno de su empresa activa
- un administrador de empresa modera solo el interno de su empresa
- un superadministrador entra ajustado al contexto activo, pero puede administrar globalmente
- una publicación interna nunca se expone a otra empresa
- un DM no se trata como post de foro
- las sanciones comunitarias solo las ejecutan administradores y superadministradores
- todas las validaciones sensibles viven en backend
- el módulo funciona de forma usable en escritorio y portátil

### Decisiones funcionales cerradas
- Reacciones: fuera de fase 1.
- Adjuntos:
  - `Público`: solo imágenes; sin archivos ni links.
  - `Interno`: archivos permitidos con retención máxima de `30 días` y purga automática obligatoria.
  - DM: sin regla adicional aprobada todavía; no se amplía alcance fuera de la base ya implementada.
- Estados de publicación:
  - mínimos operativos de fase 1: visible, moderada/oculta, cerrada y borrado lógico.
  - no se introducen borradores, fijados ni destacados en esta fase.
- Moderación:
  - administradores de empresa moderan solo el foro interno de su empresa.
  - `superadmin` modera público e interno y recibe alertas automáticas.
  - las herramientas administrativas viven detrás de un `Control` explícito, no visibles por defecto.
- Mensajería directa:
  - limitada a `1 a 1`.
  - bloqueo/reactivación de hilos ya forma parte del contrato operativo.
  - el acceso administrativo excepcional debe quedar auditado.
- Notificaciones:
  - fase 1 limitada a alertas administrativas e infracciones automáticas; no se fija aún un centro general de notificaciones de usuario.
- Búsqueda:
  - contextual por superficie (`Público`, `Mi empresa`, `Mensajes directos`).
  - no se abre todavía búsqueda avanzada multiatributo.
- Perfil comunitario:
  - se mantiene mínimo y contextual; no se abre un perfil social autónomo.
- Auditoría y cumplimiento:
  - deben auditarse infracciones automáticas, sanciones, acciones administrativas sensibles y cualquier acceso excepcional a DM.
- Límites y anti-spam:
  - queda vigente la sanción automática por links en `Público`: `7 días -> 15 días -> bloqueo_comunidad`.
  - el resto de rate limiting fino queda diferido si requiere nueva infraestructura.
- Foro público:
  - visible solo para usuarios autenticados del sistema.
- Respuestas:
  - visibles dentro del feed y sin abrir jerarquía profunda adicional en fase base.
- Edición y borrado por autor:
  - se mantiene la política conservadora de fase 1 sin ampliar permisos fuera del backend ya implantado.
- Temas y categorías:
  - la estructura oficial queda fijada como `ámbito -> categoría -> tema -> publicación -> respuesta`.
  - toda publicación debe pertenecer a un tema activo.
- Rol especializado:
  - `usuario_comunidad` queda confirmado como rol dependiente de empresa, con acceso restringido exclusivamente a `Comunidad`.

### Criterio de cierre
- La implementación posterior ya no depende de decisiones estructurales abiertas para el núcleo de `Comunidad`.
- Los puntos todavía pendientes pertenecen a evolución funcional futura, no a precondiciones bloqueantes.
