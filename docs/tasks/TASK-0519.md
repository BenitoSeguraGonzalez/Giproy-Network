# Descripción
Formalizar una política obligatoria de exactitud de cálculo, centralizar helpers operativos y reforzar módulos críticos para evitar divergencias entre BD, API y UI.

# Objetivo
Reducir a nivel mínimo el riesgo de que importes operativos visibles diverjan del cálculo persistido oficial.

# Validación
- el backend calcula importes operativos con política central
- los módulos críticos del frontend consumen helper común
- existe prueba automática que falla si se reintroducen multiplicaciones monetarias ad hoc
- el caso real `0,57 x 0,500000` mantiene `$0,29`
- `LineasPresupuestoTab` dejó de recalcular el parcial de fila con multiplicación inline y ahora usa la política común
- verificación con dato real en BD local:
  - `APU 637`
  - recurso `2-0008-00002`
  - `cantidad=0.500000`
  - `precio_congelado=0.5700`
  - `subtotal persistido=0.2900`
  - `subtotal recalculado por política=0.29`
- `Cronogramas` quedó blindado para que toda distribución persistida cierre exactamente al `100%` y el backend ya no admita overrides de línea incoherentes.
- `Desagregación` quedó alineada a `precio_total` y `subtotal` persistidos mediante helpers operativos comunes.
- `Fórmula Polinómica` dejó de expandir recursos con `precio` maestro mutable y ahora usa el costo operativo persistido del APU.
- `EDT` y `HierarchyGraphView` dejaron de recalcular directos con `precio_unitario * cantidad` y ahora consumen la misma política operativa del presupuesto.
- `FormulaPolinomicaTab` y el preview de reporting quedaron alineados con la base monetaria vigente del presupuesto y con la semántica correcta de los coeficientes.
