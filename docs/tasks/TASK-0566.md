# Descripción
La empresa `Santiago Bermeo` reporta que, tras los ajustes de sesión previos, el sistema ya no devuelve al usuario a la pantalla de login, pero sigue produciendo una actualización automática de la página que interrumpe el flujo de trabajo. Este incidente debe tratarse como continuación del frente de autenticación clásica, pero con un síntoma distinto: recarga o remontaje no deseado de la aplicación.

# Objetivo
Eliminar cualquier refresco automático o remontaje global que corte el trabajo del usuario mientras la sesión siga siendo válida, manteniendo intacta la política de sesión única, la expiración real y el aislamiento respecto a BIM.

# Contexto y relación con TASK previa
- `TASK-0565` estabilizó la expulsión al login y la renovación de token.
- El problema actual indica que persiste una interrupción del flujo, aunque ya no desemboque necesariamente en `/login`.
- Por trazabilidad y claridad operativa, este ajuste se separa como nueva TASK de hardening.

# Hallazgos preliminares
- `frontend/src/context/AuthContext.jsx` sigue conteniendo dos redirecciones duras con `window.location.href = '/login'` cuando se interpreta expiración de sesión.
- La lógica de renovación en `AuthContext` programa timers recursivos (`refreshTimeout` y `tokenTimeout`) y hoy no deja explícitamente cancelado el `tokenTimeout` anterior antes de programar el siguiente ciclo.
- Ese patrón puede generar temporizadores solapados y comportamientos tardíos que disparen una interrupción aunque ya exista un token renovado.
- El circuito actual de sesión mezcla:
  - limpieza de estado,
  - emisión de evento global,
  - redirección física,
  - y renovación anticipada.
  Esto aumenta el riesgo de remount o refresh agresivo en momentos de borde.
- En el frontend no aparecen otros candidatos fuertes de recarga automática global ligados al flujo normal de trabajo, salvo el `window.location.reload()` manual del `ErrorBoundary` y el `window.location.href = '/'` de registro, que no explican el caso reportado de uso ordinario.

# Hipótesis de causa raíz más probable
La causa más probable es un hard refresh lógico derivado del ciclo de autenticación en `AuthContext`, especialmente por timers solapados entre expiración y renovación. Aunque el usuario no termine en login, la aplicación puede estar entrando en una secuencia de limpieza/remontaje/redirección que se percibe como “actualización de página” y corta el trabajo activo.

# Conclusión de alcance
- El problema no es local de la empresa `Santiago Bermeo`.
- La causa nace en `frontend/src/context/AuthContext.jsx`, por lo que el riesgo es endémico al estado actual de la aplicación clásica para cualquier usuario autenticado bajo las mismas condiciones de sesión prolongada.

# Riesgos si no se corrige
- Pérdida de contexto operativo en proyecto/base/presupuesto.
- Interrupción de edición o navegación prolongada aunque la sesión siga siendo válida.
- Sensación de inestabilidad persistente en la empresa reportante.
- Falsos cierres de incidente al no haber logout visible, pero sí ruptura de flujo.

# Alcance propuesto
- Auditar y simplificar el ciclo completo `renovación -> expiración -> evento global -> navegación`.
- Eliminar timers solapados y cualquier hard navigation innecesaria.
- Sustituir redirecciones físicas por navegación controlada solo cuando la sesión realmente haya expirado.
- Validar que una sesión activa prolongada no recargue ni remonte la app.
- Mantener el ajuste limitado a `GiProy Clásico`.

# Implementación ejecutada
- Se eliminó la navegación dura a `/login` desde `AuthContext`; ahora la salida de sesión queda gobernada por estado React y `ProtectedRoute`, evitando recarga física del documento.
- Se endureció el ciclo de renovación de token para cancelar explícitamente timers anteriores antes de programar nuevos.
- La expiración local ahora limpia primero los timers del ciclo para evitar disparos tardíos de expiración sobre tokens ya renovados.
- Se confirma que el defecto es endémico al frontend clásico y no un dato local exclusivo de `Santiago Bermeo`.

# Validación ejecutada
- `npm run build` en `frontend` completado correctamente tras el ajuste.
- Revisión de impacto: el cambio quedó acotado a `frontend/src/context/AuthContext.jsx` y documentación operativa.
- No se modificaron rutas, componentes ni flags BIM.

# Plan de trabajo
1. Reproducir lógicamente el ciclo de timers y documentar exactamente dónde puede producirse el remount.
2. Desacoplar la renovación de token de la expiración dura para que nunca convivan timers anteriores y nuevos.
3. Convertir la reacción a expiración real en una sola ruta de salida, sin duplicar limpieza + evento + hard redirect.
4. Revisar si `checkAuth()` o el bootstrap del layout reinyectan un remount visible tras renovar token.
5. Validar sesión prolongada y navegación continua sobre módulos clásicos de uso real.
6. Documentar criterios finales de cierre del incidente.

# Criterios de validación
- El usuario puede permanecer trabajando más allá del umbral previo sin:
  - volver al login,
  - recargar el documento,
  - perder el contexto activo del módulo.
- La renovación del token ocurre sin navegación visible ni remount perceptible.
- La expiración real, revocación o sesión sustituida siguen cerrándose correctamente.
- No se modifica ni activa ninguna ruta o capacidad BIM.

# Impacto esperado
- Mayor estabilidad percibida en la empresa `Santiago Bermeo`.
- Flujo continuo de trabajo en módulos clásicos.
- Separación clara entre “sesión inválida” y “renovación transparente”.
