# Descripción
El marketplace clásico ya cuenta con catálogo, compra, biblioteca, panel vendedor y moderación administrativa, pero el gestor de items aún está incompleto para una tienda multi vendedor madura. Este slice busca cerrar la brecha principal del panel vendedor y mejorar el descubrimiento del catálogo sin introducir acoplamientos con BIM.

# Objetivo
Completar el siguiente nivel operativo del Marketplace clásico para que el vendedor pueda administrar mejor sus productos y el catálogo exponga categorías y filtros reales de navegación.

# Alcance
- Añadir gestión visible de productos del vendedor sobre la UI clásica existente.
- Incorporar categorías reales en el flujo de publicación/edición y en el catálogo.
- Mejorar búsqueda y filtros del marketplace para hacerlo consistente con el resto de GiProy.
- Sustituir feedbacks nativos agresivos por diálogos del sistema donde corresponda.
- Mantener el ajuste limitado a la capa clásica.

# Hallazgos de partida
- El backend ya soporta `category_id` y `updateSellerProduct`, pero la UI clásica no expone un gestor completo del item.
- El vendedor hoy puede publicar y listar, pero no administrar claramente el ciclo de vida del producto desde el panel.
- El catálogo no usa todavía categorías visibles pese a existir `GET /marketplace/categories`.
- Persisten `alert(...)` nativos en seller/admin, lo que desalineaba la UX con el resto del sistema.

# Plan de trabajo
1. Promover la sesión a una TASK específica de Marketplace clásico.
2. Completar el panel vendedor con edición operativa y activación/desactivación.
3. Exponer categorías en publicación, edición y catálogo.
4. Endurecer búsqueda y filtros del catálogo.
5. Reemplazar feedbacks nativos por `appAlert`.
6. Validar compilación frontend y no interferencia con BIM.

# Criterios de validación
- El vendedor puede editar un producto existente desde su panel.
- El vendedor puede activar o desactivar un producto sin salir del panel.
- Las categorías se pueden seleccionar y ver en el marketplace clásico.
- El catálogo puede filtrarse por categoría además de tipo y texto.
- La búsqueda visible de Marketplace sigue una normalización robusta.
- No se activan rutas, flags ni superficies BIM.

# Riesgos a vigilar
- No tocar contratos de backend innecesariamente si el soporte ya existe.
- No introducir dependencias entre Marketplace y módulos BIM.
- No romper el flujo actual de compra, moderación o biblioteca.

# Implementación ejecutada
- Se completó el panel vendedor clásico con edición operativa de productos ya publicados usando el endpoint existente `updateSellerProduct`.
- Se añadió activación y desactivación rápida de productos desde el listado del vendedor, manteniendo el mismo backend común y sin introducir endpoints nuevos.
- Se incorporó selección de categoría en el formulario de publicación y edición, reutilizando `GET /marketplace/categories`.
- El catálogo clásico ahora expone filtro por categoría y usa búsqueda normalizada consistente con el resto del frontend visible.
- El detalle de producto y la moderación admin muestran también la categoría del item cuando existe.
- Los `alert(...)` nativos del seller/admin marketplace fueron sustituidos por `appAlert` y `appConfirm` para alinear la UX con el sistema.

# Validación ejecutada
- `npm run build` completado correctamente en `frontend`.
- Revisión de alcance: no se modificó backend de negocio, flags BIM, rutas BIM ni componentes BIM.
- Verificación funcional del slice: vendedor ahora puede publicar, editar y activar/desactivar; catálogo ahora puede navegarse por tipo, categoría y texto.

# Resultado
- Marketplace clásico queda más cerca de un gestor real de items multi vendedor y deja de depender solo de “publicar + listar”.
- La evolución es invisible para BIM y no introduce acoplamiento prematuro hacia esa capa.
