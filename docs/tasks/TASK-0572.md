# Descripción
El administrador de la empresa `Santiago Bermeo` sigue siendo expulsado a la pantalla de login con el mensaje `Su sesión ha expirado. Vuelva a iniciarla.`. El frente había sido saneado parcialmente, pero la incidencia funcional no puede darse por cerrada.

# Objetivo
Determinar qué parte del flujo de sesión clásica sigue rota y preparar el siguiente ajuste correctivo sin interferir con BIM ni con el backend común.

# Alcance
- Reabrir la investigación del circuito `401 -> expiración -> login`.
- Confirmar si la causa remanente es local de la empresa o endémica al estado actual de la app.
- Dejar hipótesis priorizadas y slice siguiente de corrección.

# Análisis actual
- La captura aportada muestra el mensaje exacto `Su sesión ha expirado. Vuelva a iniciarla.`, que hoy puede venir del backend por `JWT expirado` o del ciclo frontend cuando fuerza expiración con ese mismo mensaje.
- En `backend/app/api/deps.py` el backend sigue cerrando sesión por tres vías legítimas:
  - `JWT exp` vencido
  - `sid` inválido por reemplazo o revocación
  - inactividad real
- En las trazas existentes de `backend/auth_debug.log` para `santibq81@msn.com` no aparece evidencia visible de `sid mismatch` en las muestras revisadas; las comprobaciones observadas mantienen `TokenSID == DBSID`.
- El frontend sigue teniendo un punto débil estructural en `frontend/src/api/axiosConfig.js`: cualquier `401` dispara `expireAuthSession(...)` de forma inmediata y global.
- A la vez, `frontend/src/context/AuthContext.jsx` mantiene renovación programada de token y varios consumers que generan tráfico en segundo plano (`/usuarios/me`, licencia, comunicados, mantenimiento, etc.).

# Hipótesis principal
Existe una carrera entre renovación de token y peticiones concurrentes en segundo plano:
- una request sale todavía con el token viejo o ya vencido,
- recibe `401`,
- el interceptor expira toda la sesión al primer `401`,
- aunque la renovación pudiera recuperarse o el fallo fuera transitorio.

Esto convierte cualquier `401` puntual en logout forzado y hace que el problema sea potencialmente endémico al estado actual del frontend clásico, no exclusivo de `Santiago Bermeo`.

# Hipótesis secundarias
- `checkAuth()` limpia sesión ante cualquier error de `/usuarios/me`, aunque el error no sea estrictamente una expiración real.
- En segundo plano siguen existiendo llamadas periódicas que pueden tocar el token cerca del borde de expiración.
- Si el navegador suspende timers en background, el refresh puede llegar tarde y el primer request al volver reactiva el circuito agresivo de logout.

# Implementación ejecutada
- Se rehízo el manejo de `401` en `frontend/src/api/axiosConfig.js` para coordinar recuperación de sesión:
  - se detecta si el token ya fue renovado por otra request y se reintenta con el token nuevo
  - se serializa un único refresh compartido para evitar carreras paralelas
  - se reintenta la request original tras refresh exitoso
  - solo se expira la sesión cuando el refresh falla de forma definitiva o la request ya fue reintentada
- Se endureció `checkAuth()` en `frontend/src/context/AuthContext.jsx` para que no limpie la sesión por cualquier error transitorio distinto de `401`.
- Se añadió trazabilidad estructurada de sesión extremo a extremo:
  - backend JSONL en `backend/app/core/session_trace.py`
  - `request_id` por request desde `backend/app/main.py`
  - clasificación backend en `backend/app/api/deps.py` y `backend/app/api/endpoints/auth.py`
  - canal de eventos frontend hacia `POST /api/v1/login/session-trace`
  - emisor frontend en `frontend/src/utils/sessionTrace.js`
- El archivo de seguimiento queda por defecto en `auth_session_trace.jsonl`, configurable desde `AUTH_SESSION_TRACE_FILE`.

# Validación
- `npm run build` en `frontend` completado correctamente.
- `python -m py_compile backend/app/core/config.py backend/app/core/session_trace.py backend/app/main.py backend/app/api/deps.py backend/app/api/endpoints/auth.py` completado correctamente.

# Resultado de esta iteración
La incidencia deja de depender de un logout global al primer `401` recuperable. Además, a partir de esta iteración ya existe evidencia técnica suficiente para identificar la causa raíz real del próximo corte de sesión con correlación entre backend y frontend.

- No se requiere seguir recolectando evidencia para este frente salvo que reaparezca una regresión nueva.
