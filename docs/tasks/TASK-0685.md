# Descripción
Plan maestro para convertir `Portal de compras públicas` en un artículo híbrido de Tienda que combine:
- entrega comercial tipo marketplace
- exportación/importación técnica basada en el importador externo existente
- provisión automática de un proyecto adquirido listo para trabajar en el sistema comprador

Además, este plan deja explícito que el importador externo actual será retirado como herramienta operativa independiente una vez que su funcionalidad útil quede absorbida en la capa nativa del sistema.

# Análisis actual

## 1. Importador externo existente
- Existe un importador externo en [`apoyo/apu_extractor.py`](/e:/Repositorios/GiProy%20Network/apoyo/apu_extractor.py).
- Hoy es una pieza separada de la capa clásica y no está integrada al flujo de `Marketplace`.
- Su orientación actual es de extracción / normalización / exportación técnica, con generación de hojas tipo Excel.
- La dirección objetivo ya no es mantenerlo como herramienta viva separada, sino absorber su lógica útil y retirar su papel operativo externo.

## 2. Marketplace ya tiene entrega postcompra
- El checkout actual ya entrega activos adquiridos según tipo en [`marketplace_checkout.py`](/e:/Repositorios/GiProy%20Network/backend/app/services/marketplace_checkout.py).
- Ya existe biblioteca de comprador y trazabilidad de origen adquirido.
- Los activos adquiridos ya se marcan como `acquired` mediante [`marketplace_asset_origin.py`](/e:/Repositorios/GiProy%20Network/backend/app/services/marketplace_asset_origin.py).

## 3. Política actual de activo adquirido
- El sistema ya distingue `propio` vs `adquirido`.
- Ya existe política activa para impedir republicación en marketplace de activos adquiridos.
- Esto nos da una base útil para añadir nuevas restricciones futuras sin rehacer todo el modelo.

## 4. Proyecto y base de trabajo
- El modelo [`Proyecto`](/e:/Repositorios/GiProy%20Network/backend/app/models/proyecto.py) permite `base_trabajo_id = null`.
- Eso hace viable la regla inicial pedida:
  - el proyecto entregado por este artículo puede crearse sin base madre
- Lo que aún no existe como regla explícita es:
  - bloqueo de envío
  - marcador específico de “proyecto adquirido desde Portal de compras públicas”

# Objetivo funcional
Cuando el superadministrador cree un artículo de `Portal de compras públicas`, podrá definir:
- metadatos comerciales del producto
- metadatos exclusivos de licitación
- una configuración híbrida de importación/entrega

Cuando un usuario compre ese artículo:
- recibirá un proyecto listo en su sistema
- ese proyecto contendrá el contenido importado/preparado asociado al artículo
- el proyecto quedará marcado como adquirido
- inicialmente no tendrá base madre
- inicialmente no podrá ser enviado

# Objetivo estructural adicional
Retirar el importador externo como pieza operativa separada, dejando toda su funcionalidad absorbida en servicios internos del sistema.

# Alcance propuesto

## Fase 1. Modelo híbrido del producto
Extender el creador/editor de `Portal de compras públicas` para soportar una configuración de entrega híbrida:
- `delivery_mode`
  - `excel_only`
  - `project_only`
  - `excel_and_project`
- `import_source`
  - archivo plantilla/subido
  - configuración manual mínima
- `project_delivery_policy`
  - `create_project_on_purchase = true`
  - `project_without_base = true`
  - `project_send_locked = true`

## Fase 2. Importador integrado al artículo
Integrar una primera versión controlada del importador dentro del creador del artículo:
- permitir subir archivo origen del portal
- procesarlo o dejarlo preparado para procesamiento posterior
- generar activo técnico reutilizable por el checkout
- guardar suficiente metadata para reproducir la entrega

Esta fase ya debe pensarse como migración de lógica desde el importador externo hacia una implementación nativa.

## Fase 3. Entrega postcompra
Ampliar el checkout de marketplace para `portal_compras_publicas`:
- detectar producto de este tipo
- generar proyecto nuevo en la empresa compradora
- dejarlo listo para uso
- registrar origen adquirido marketplace
- aplicar política inicial:
  - sin base madre
  - no enviable

## Fase 4. Biblioteca y trazabilidad
La biblioteca del comprador debe mostrar este activo como proyecto adquirido especial:
- tipo: `portal_compras_publicas`
- origen: marketplace
- política: adquirido / no republicable
- futura política ampliable

# Decisiones de diseño ya recomendadas

## 1. No integrar directamente `apoyo/apu_extractor.py` dentro del request web
La pieza externa debe desmontarse y absorberse en servicios reutilizables; no debe llamarse tal cual desde UI o endpoint.

## 2. Separar tres capas
- UI de creador del artículo
- servicio de importación / preparación técnica
- servicio de entrega postcompra

## 3. Marcar explícitamente este proyecto con metadata propia
No basta solo con `MarketplaceAssetOrigin`. Hace falta además una metadata específica del proyecto entregado para:
- distinguirlo de otros proyectos comprados
- bloquear envío
- reconocer que no tiene base madre por diseño

## 4. No ampliar todavía políticas globales complejas
La primera iteración debe dejar:
- restricción de envío
- origen adquirido
- sin base madre

Y posponer para después:
- clonación permitida o no
- edición restringida por secciones
- expiración de licencias o vigencia comercial
- redistribución interna avanzada

# Riesgos a controlar
- acoplar demasiado el importador externo al request HTTP
- mezclar lógica comercial y lógica de importación en el mismo endpoint
- crear proyectos inválidos si la importación falla a mitad
- no dejar trazabilidad suficiente para soporte posterior
- bloquear de forma ambigua el envío sin un marcador explícito

# Estrategia de implementación recomendada
1. Formalizar schema y metadata del producto híbrido.
2. Extraer y absorber la lógica útil del importador externo en servicios internos.
3. Añadir persistencia de configuración híbrida al artículo.
4. Implementar entrega postcompra de proyecto adquirido.
5. Añadir bloqueo inicial de envío.
6. Exponer lectura clara en biblioteca / origen del activo.
7. Retirar el importador externo como herramienta operativa separada.

# Criterios de aceptación
- El creador de `Portal de compras públicas` permite definir la modalidad híbrida.
- El artículo guarda la configuración técnica mínima necesaria.
- Al comprarlo, el sistema crea un proyecto listo para trabajo.
- El proyecto queda marcado como adquirido y no enviable.
- El proyecto no depende de base madre.
- La biblioteca permite identificar claramente el activo adquirido.
- La funcionalidad ya no depende operativamente de [`apoyo/apu_extractor.py`](/e:/Repositorios/GiProy%20Network/apoyo/apu_extractor.py).
