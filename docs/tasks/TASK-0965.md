# TASK-0965 - Rollback Compensatorio De Aplicación Por Partidas

## Modo
GIPROY CLASICO

## Estado
Completada - Slice 1

## Objetivo
Endurecer la acción `Aplicar por partidas` del flujo `Caja -> Valorado` para evitar estados parcialmente persistidos si falla una actualización intermedia.

## Alcance
- Mantener la aplicación por partidas con confirmación explícita.
- Usar solo endpoints existentes del Cronograma Valorado.
- Revertir en backend las líneas que sí alcanzaron a guardarse antes del error.
- No crear API nueva.
- No mover fechas, dependencias, recursos ni calendario del Gantt.

## Implementación Slice 1
- Antes de aplicar la propuesta se captura el estado anterior de cada línea afectada.
- Cada línea guardada se registra en una lista de aplicación efectiva.
- Si ocurre un fallo, el frontend ejecuta rollback compensatorio en orden inverso:
  - si la línea tenía override previo, lo restaura con `updateValoradoLinea`;
  - si la línea no tenía override previo, elimina el override nuevo con `resetValoradoLinea`.
- Si el rollback compensatorio falla parcialmente, el modal de error lo comunica para revisión manual con `Limpiar overrides`.

## Criterios De Aceptación
- Un fallo intermedio no deja silenciosamente el estado local como si todo hubiera aplicado.
- Las líneas ya guardadas antes del fallo intentan volver a su estado anterior en backend.
- El Gantt no se modifica.
- No se añade endpoint nuevo ni persistencia paralela.
