# TASK-1180 - Corrección de autoridad temporal de predecesoras en Gantt clásico

## Objetivo
Corregir la regresión detectada en `Santiago Bermeo` donde las relaciones `Predecesoras` se guardaban correctamente, pero la tarea destino seguía usando `start_date/end_date` explícitos antiguos, provocando un Gantt visualmente incompatible con la política `FC/CC/FF/CF`.

## Causa raíz
- `cronogramas_trabajo` priorizaba `override.start_date` antes que las dependencias.
- El frontend persistía relaciones y fechas explícitas en el mismo payload.
- El backend aceptaba la fecha explícita como autoridad, dejando la relación como dato/dibujo sin reprogramación efectiva.

## Regla correctiva obligatoria
1. Si una tarea tiene `dependencies` o `predecessors`, la relación manda.
2. `start_date` y `end_date` explícitos solo se respetan cuando la tarea no tiene dependencias activas.
3. `FC/CC/FF/CF` deben reprogramar la tarea destino en backend, no solo en frontend.
4. La respuesta de `cronogramas_trabajo` debe devolver fechas ya gobernadas para que el Gantt no dependa de correcciones visuales.

## Alcance autorizado
- Backend común de `cronogramas_trabajo`.
- QA real sobre `Santiago Bermeo`.
- Documentación `TASK` y `CHANGELOG`.
- Sin activar UX BIM.
- Sin introducir acoplamientos hacia BIM.

## Criterios de aceptación
- Una relación `FC` mueve el inicio destino al fin origen más lag.
- Una relación `FF` ajusta el inicio destino para que su fin coincida con el fin origen más lag.
- Una relación guardada no puede quedar subordinada a un `start_date` explícito antiguo.
- El caso real `Santiago Bermeo` deja de mostrar líneas en enero cuando sus predecesoras las gobiernan desde marzo/abril.
- `npm run smoke:gantt-classic`, smoke real backend y build pasan.

## Implementación
- `cronograma_trabajo` resuelve primero las dependencias y solo acepta `start_date/end_date` explícitos cuando la fila no está gobernada por predecesoras.
- El cálculo de fin por duración laboral usa el inicio real de la jornada del día, evitando que `FF/CF` compriman o desplacen el cierre por tomar la hora actual como inicio de jornada.
- El frontend clásico deja de anteponer snapshots pendientes antiguos a las fechas devueltas por backend cuando la tarea tiene dependencias activas.
- El timeline clásico resuelve localmente el grafo de dependencias antes de pintar, para que las barras se recoloquen de inmediato y las líneas no sean solo decorativas si el refresco backend aún no ha propagado.
- La confirmación de shortcodes con varias predecesoras usa la restricción dominante, no la última relación escrita.
