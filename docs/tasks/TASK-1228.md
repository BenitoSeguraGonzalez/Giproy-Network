# TASK-1228 - Permitir predecesoras posteriores sin romper logica tipo Project

## Modo
GIPROY CLASICO

## Objetivo
Corregir el rechazo de shortcodes como `10FC` cuando la tarea predecesora esta despues de la tarea receptora en el grid.

## Causa
Persistia una politica antigua que obligaba a que toda predecesora fuese una partida anterior por orden de listado. Esa regla no es compatible con la logica tipo MS Project: la posicion visual o numerica de fila no define si una relacion es valida.

## Implementacion
- Backend: se elimina la validacion `solo puede depender de partidas anteriores`.
- Backend: se conserva la validacion de partida calculable existente.
- Backend: se bloquea la dependencia contra si misma.
- Backend: se incorpora deteccion de ciclos sobre el grafo completo de dependencias antes de persistir.
- Frontend Gantt: el selector de predecesoras deja de limitar candidatos a filas anteriores y muestra cualquier otra partida calculable.
- Frontend Cronograma Valorado: se alinea la validacion para no rechazar predecesoras posteriores por orden.

## Validacion
- `python -m py_compile backend/app/services/cronograma_trabajo.py` completado correctamente.
- `npm run build` completado correctamente.
- Busqueda `rg` confirma que ya no queda el mensaje ni la regla antigua de "partidas anteriores" en las rutas afectadas.

## No interferencia BIM
- No se modifican componentes BIM.
- No se activa UX BIM.
- No se introduce dependencia hacia BIM.
