## Hipotesis tecnica
La aceptacion de una secuenciacion parece lenta porque, tras guardar el Gantt, el flujo espera tambien la resincronizacion silenciosa del Cronograma Valorado cuando el modo es `gantt`. Ese segundo trabajo puede tardar lo suficiente para que la UI parezca no responder, aunque el Gantt ya haya persistido.

## Impacto en licencias
- Sin modulo nuevo.
- Endpoint nuevo acotado al modulo existente de cronogramas, bajo las mismas validaciones de empresa, permisos y licencias.
- Se conservan permisos y tenant del backend actual.

## Impacto UI
- Sin rediseño.
- Se permitira feedback de guardado/sincronizacion no bloqueante.

## Implementacion aplicada
- `Cronogramas.jsx` permite diferir la sincronizacion silenciosa del Cronograma Valorado cuando el commit del Gantt llega con `deferValoradoSync`.
- La sincronizacion diferida usa debounce de `900 ms` para agrupar secuenciaciones consecutivas y se ejecuta en segundo plano.
- `CronogramaGantt.jsx` marca las nuevas secuenciaciones tarea-tarea y hito-tarea con `deferValoradoSync: true`.
- El Gantt muestra aviso de secuencia guardada mientras el Valorado queda sincronizandose en segundo plano si aplica.
- `Cronogramas.jsx` estabiliza la respuesta `CronogramaTrabajoResponse` reutilizando filas y entradas `schedule_data` equivalentes para evitar rerenders innecesarios del Gantt tras el guardado backend.
- Backend anade `PUT /cronogramas-trabajo/{presupuesto_id}/commit-delta` para validar y persistir igual que el commit completo, pero devolver solo filas livianas de programacion, `schedule_data` cambiado y resumen.
- `Cronogramas.jsx` usa `updateTrabajoDelta(...)` solo cuando el commit viene de secuenciacion Gantt con `deferValoradoSync`; el resto de guardados conserva el contrato completo.
- La fusion delta conserva metadata pesada previa y solo sobreescribe claves de programacion/CPM recibidas.
