# TASK-1637 - Control visual del editor APU en Presupuesto

## Modo

GIPROY CLASICO.

## Estado

Abierta / en curso.

Esta TASK no debe cerrarse hasta que el usuario confirme que la ronda visual del editor APU queda satisfecha. Funciona como carril de control para ajustes incrementales sobre el editor APU usado desde `Presupuesto`.

## Contexto

Se confirmo que actualmente existen dos puntos de entrada para editar APUs:

- `frontend/src/components/presupuestos/ApuEditorModal.jsx` + `frontend/src/components/presupuestos/ApuBudgetEditor.jsx`: editor inline/drawer usado desde Presupuesto.
- `frontend/src/pages/APUs.jsx`: editor padre dentro del modulo de APUs, diferido para una fase posterior.

La unificacion en una sola ruta se considera riesgosa para esta fase porque el editor de Presupuesto necesita conservar contexto, cierre inline, refresco del presupuesto y retorno sin sacar al usuario del grid operativo. Por tanto, esta TASK no busca consolidar arquitectura ni crear componente comun todavia.

Actualizacion de premisa del 2026-05-13: se suspende la aplicacion doble. Desde este punto, los ajustes activos de esta TASK se haran solo sobre el editor APU de Presupuesto. El editor padre de `APUs` queda congelado/diferido hasta nueva orden expresa.

## Premisa de trabajo

- Primero se trabajara solo la capa visual.
- No se hara una ruta unica para ambos editores.
- No se extraera un componente comun en esta TASK salvo autorizacion posterior explicita.
- Todo ajuste visual solicitado desde este punto aplica solo al editor APU de Presupuesto (`ApuBudgetEditor`).
- El editor padre de `APUs` no se tocara en esta TASK salvo orden expresa posterior.
- La adecuacion visual debe mantenerse sin alterar comportamiento, handlers, payloads, guardado, navegacion, APIs, calculos, persistencia ni backend.
- Si mas adelante se decide consolidar componente comun, debera abrirse o promoverse una TASK tecnica separada, con analisis propio y slices seguros.

## Alcance permitido

- Ajustes visuales de layout, densidad, header, botones, cards, tablas, scroll, estados visuales y jerarquia del editor APU.
- Adecuacion visual de `ApuBudgetEditor` dentro de Presupuesto.
- Uso de componentes UI existentes si no cambia la operativa.
- Documentacion incremental de cada ajuste visual incorporado.

## Alcance prohibido

- No tocar backend.
- No tocar PostgreSQL.
- No cambiar contratos API.
- No cambiar calculos de APU, rendimiento, cantidades, costos o subtotales.
- No modificar reglas de guardado, confirmacion, descarte, APU anidado o propagacion.
- No cambiar rutas ni forzar navegacion unica.
- No introducir componente comun sin autorizacion expresa.
- No crear dependencias hacia BIM.

## Ajustes pendientes centralizados

### Plan de adecuacion visual inicial

#### Objetivo visual

Adecuar progresivamente el editor APU usado desde `Presupuesto` al lenguaje visual que se esta aplicando en GiProy Clasico: uso moderado de headers tecnicos, controles iconograficos sobrios, densidad operativa, cards tecnicas ligeras, listados compactos y lectura clara de codigo, descripcion, unidad, rendimiento, costo y acciones.

El resultado esperado no es una unificacion tecnica ni una paridad inmediata con `APUs.jsx`, sino una mejora visual controlada del editor operativo de Presupuesto.

#### Diagnostico de partida

- `ApuBudgetEditor` ya funciona como drawer/editor inline de Presupuesto y conserva contexto operativo de presupuesto.
- `APUs.jsx` concentra catalogo, modulo padre y editor en una pagina monolitica, pero queda fuera del alcance activo de esta ronda.
- El riesgo principal no esta en las clases visuales aisladas, sino en tocar accidentalmente handlers, payloads, guardado, APU anidado, estados dirty o navegacion.

#### Criterios rectores

- Cada ajuste se aplicara solo en `ApuBudgetEditor`, salvo autorizacion expresa para extenderlo al editor padre de `APUs`.
- Ningun lote debe modificar funciones de carga, guardado, calculo, confirmacion, navegacion o persistencia.
- No se movera el flujo de Presupuesto hacia `/apus`.
- No se extraera componente comun durante esta fase.
- Si una idea visual debe reservarse para `APUs.jsx`, se documentara como diferida y no se implementara en esta TASK.

#### Lote 1 - Header del editor APU

Objetivo:

- Ajustar la cabecera del editor APU en Presupuesto.
- Usar una jerarquia tecnica compacta:
  - codigo APU visible
  - descripcion legible
  - estado/revision como chip discreto
  - contexto de origen si se edita APU anidado
  - acciones principales como botones con icono

Ajustes previstos:

- Reducir peso de cabecera clara actual de `ApuBudgetEditor`.
- Alinear acciones `Cerrar`, `Guardar`, `Volver al padre` con el patron de botones iconograficos/tecnicos vigente.
- Reducir el exceso de negro del header actual y buscar una cabecera menos pesada, mas integrada con el area de formulario.
- Mantener copy `Nivel Presupuesto` solo si aporta contexto y no domina visualmente.

Valoracion:

- Coste: medio-bajo.
- Riesgo: bajo si se limita a JSX/clases y no se tocan callbacks.

#### Lote 2 - Panel izquierdo de recursos/catalogo

Objetivo:

- Ajustar el panel de recursos disponibles del editor de Presupuesto.
- Reducir sobrepeso visual y acercarlo al patron aplicado en el catalogo APU de Presupuesto.

Ajustes previstos:

- Header lateral mas tecnico y compacto.
- Buscador con el skin actual del grid/listado de Presupuesto.
- Categorias y subcategorias con cards mas sobrias, borde sutil y contador discreto.
- Boton de colapso/expansion alineado con los botones circulares/soft que ya se estan usando.
- Evitar sombras fuertes, halos y tarjetas dentro de tarjetas.

Valoracion:

- Coste: medio.
- Riesgo: medio-bajo; se debe cuidar que solo cambie presentacion.

#### Lote 3 - Formulario superior del APU

Objetivo:

- Convertir la zona de datos del APU en una banda tecnica compacta, coherente con Datos de Proyecto, Gantt y Presupuesto.

Ajustes previstos:

- Descripcion, unidad, estado de revision, rendimiento global y OmniClass deben verse como campos tecnicos organizados, no como card pesada.
- Mantener campos editables existentes y sus mismos eventos.
- Reubicar chips de estado para que no compitan con los inputs principales.
- Evitar que `OmniClass` ocupe una banda dominante si no esta desplegado.

Valoracion:

- Coste: medio.
- Riesgo: bajo-medio por formularios y selectores; no cambiar componente ni contrato de `onChange`.

#### Lote 4 - Tabla/listado de composicion APU

Objetivo:

- Homologar la tabla de recursos del APU con la densidad del grid de Presupuesto: filas mas tecnicas, encabezado tecnico segun contexto, acciones iconograficas y subtotales legibles.

Ajustes previstos:

- Header de columnas mas alineado con el grid de Presupuesto.
- Filas menos altas, con descripcion/codigo/unidad/cantidad/rendimiento/precio/parcial en lectura clara.
- Inputs numericos con menor altura visual sin sacrificar edicion.
- Acciones de editar recurso, editar APU anidado, borrar y arrastrar en formato iconografico consistente.
- Subheaders por categoria con lectura tipo seccion tecnica, no bloques altos.

Valoracion:

- Coste: medio-alto.
- Riesgo: medio, porque hay drag/drop, inputs y acciones por fila. Debe hacerse con cambios visuales localizados y validacion cuidadosa.

#### Lote 5 - Estados de APU anidado y retorno al padre

Objetivo:

- Homologar la lectura de APU anidado dentro del editor de Presupuesto.
- Mantener visible el origen y retorno sin crear banners pesados.

Ajustes previstos:

- Banda contextual compacta con codigo/descripion del padre.
- Boton `Volver al padre` con patron iconografico/tecnico.
- Mantener confirmaciones existentes intactas.
- Evitar duplicar contexto si ya aparece en el header.

Valoracion:

- Coste: bajo.
- Riesgo: bajo si no se toca la logica de historial.

#### Lote 6 - Footer, totales y feedback de guardado

Objetivo:

- Dar cierre visual al editor con lectura economica clara y feedback consistente.

Ajustes previstos:

- Totales del APU como capsulas tecnicas sobrias.
- Boton de guardar destacado pero alineado con el sistema.
- Toast/feedback sin peso excesivo.
- Estados `Guardando`, deshabilitado y error con semantica visual clara.

Valoracion:

- Coste: medio.
- Riesgo: bajo-medio, cuidando no alterar eventos de guardado.

#### Lote 7 - Responsive y drawer

Objetivo:

- Verificar que el editor inline de Presupuesto mantiene area util en resoluciones bajas.

Ajustes previstos:

- Ajustar solo clases de layout visual.
- Mantener el cierre/retorno del drawer de Presupuesto.
- No cambiar reglas actuales de colapso, salvo correcciones visuales estrictamente necesarias.

Valoracion:

- Coste: medio.
- Riesgo: medio por interaccion con paneles colapsables.

#### Orden recomendado

1. Header del editor APU.
2. Panel izquierdo de recursos/catalogo.
3. Formulario superior del APU.
4. Tabla/listado de composicion.
5. APU anidado y retorno.
6. Footer/totales/feedback.
7. Responsive/drawer.

#### Criterio de aceptacion por lote

- El ajuste mejora `ApuBudgetEditor` sin depender de `APUs.jsx`.
- No cambia ningun handler ni payload.
- No cambia calculo ni persistencia.
- No cambia ruta ni navegacion base.
- No introduce referencias BIM.
- Build frontend OK.
- Smoke no contaminacion BIM OK.
- Revision visual antes/despues sobre editor APU abierto desde una linea de Presupuesto.

#### Congelador / rollback visual

La reversibilidad queda basada en el diff de esta TASK y sus lotes. Cada lote debe quedar documentado antes de cerrar turno para poder revertir el ultimo bloque visual sin afectar operativa.
