GIPROY CLASICO.

## Objetivo
Sanear `Configuracion > Gestion de usuarios` en la capa clasica para que listado, alta, edicion, validacion y borrado funcionen de forma coherente para administrador y superadministrador sobre la empresa `Santiago Bermeo`, sin activar ni contaminar BIM.

- QA focal de jerarquia/perfil de usuarios: `backend/app/tests/test_usuario_admin_profile_hierarchy.py`.

## Implementacion
- `UsuarioResponse` normaliza a lista vacia los campos tipo lista que pueden venir nulos desde datos historicos:
  - `marketplace_permissions`
  - `marketplace_profile_missing_fields`
  - `marketplace_profile_missing_labels`
- Se agrega prueba de regresion para confirmar que un usuario legacy con `marketplace_permissions = None` serializa como `[]`.
- La correccion queda en el schema compartido, por lo que protege tambien otros endpoints que serializan usuarios asignados desde ORM.
- Se sanea el submit del modal de usuarios para enviar solo campos permitidos al backend, evitando arrastrar objetos ORM (`empresa`), fechas o campos calculados de Marketplace en edicion.
- En edicion, la confirmacion de contrasena solo se valida si el usuario esta cambiando la contrasena; dejar ambos campos vacios conserva la clave actual.
- El formulario de personal deja de exigir RUC en edicion para no bloquear usuarios historicos incompletos con validacion nativa del navegador.
- El rol `Superadministrador` solo queda disponible en la superficie `Ajuste SaaS`; en `Gestion de usuarios` de empresa, incluso si opera un superadministrador, no se mezcla con el staff de empresa.
- Al crear usuarios desde superadministracion, el formulario toma como empresa objetivo la empresa activa seleccionada, manteniendo el parametro `empresa_id` explicito del endpoint.
- `AppModalShell` recupera compatibilidad con render condicional: si el componente ya se monta solo cuando debe abrirse, `isOpen` toma `true` por defecto. Esto corrige que los botones `Editar`/`Anadir` cambiaran estado pero no mostraran modal.
- Las acciones de usuarios quedan visibles y clicables de forma permanente, con `type="button"` explicito para evitar submits accidentales.
- El cambio de pestana limpia busqueda, seleccion, modo edicion, previews y modales abiertos para evitar estado arrastrado entre `Gestion de usuarios` y `Ajuste SaaS`.
- El backend rechaza duplicados de email dentro de la misma empresa tambien al editar, normalizando espacios y comparando sin depender de mayusculas/minusculas.
- El alta normaliza email y nombre antes de validar cuotas/duplicados.
- El repositorio de usuarios incorpora eliminacion real (`remove`), cerrando el fallo interno del endpoint de borrado que llamaba a un metodo inexistente.
- El borrado captura la empresa antes de eliminar para actualizar metricas sin depender de un objeto ORM ya eliminado.

- Sin cambios de base de datos ni migraciones.
