# TASK-1693 - Restauracion Cloudflared desde backup y diagnostico de ingress remoto

> Nota de cierre posterior: esta TASK queda como antecedente historico. `TASK-1694` elimina el tunel dedicado temporal, devuelve `giproy-network.excompc.dpdns.org` al tunel `eXcom-SaaS` y restaura GiProy en `localhost:3010`.

Fecha: 2026-05-19

Modo: GIPROY CLASICO

## Objetivo

Analizar `CloudFlared-bkp`, recuperar la estructura local de servicios Cloudflared y determinar por que `https://giproy-network.excompc.dpdns.org` seguia roto despues de restaurar el frontend clasico a `localhost:5173`.

## Alcance autorizado

- Infraestructura local de tuneles Cloudflared.
- Servicios Windows restaurados desde backup NSSM.
- Validacion de conectividad contra el frontend clasico en `5173`.

Sin cambios funcionales en backend, frontend de producto o capa BIM.

## Hallazgos

- El backup define dos servicios locales, no un servicio generico unico:
  - `cloudflared-eXcom` para el tunel `eXcom-SaaS`.
  - `cloudflared-SaaS` para el tunel `giproy-erp-beta`.
- El error `1033` desaparece al restaurar los servicios: Cloudflare vuelve a resolver el conector.
- La URL publica pasa a `404 Not Found`, lo que confirma que el conector existe pero el hostname no entra por una regla de ingress valida.
- El log de diagnostico de `cloudflared` confirma que el tunel `giproy-erp-beta` recibe configuracion remota y sobreescribe el `--url` local.
- La configuracion remota vigente contiene ingress para:
  - `giproy-erp.excompc.dpdns.org` hacia `http://localhost:8000`.
  - `web-giproy.excompc.dpdns.org` hacia `http://localhost:80`.
  - fallback `http_status:404`.
- `giproy-network.excompc.dpdns.org` no aparece en la configuracion remota de ingress, por eso cae en el fallback 404.

## Implementacion local

- Se agrega `CloudFlared-bkp/restore_from_backup.ps1` para reconstruir los servicios Windows desde los archivos NSSM del backup usando el `cloudflared.exe` instalado y el NSSM local del repo.
- El script elimina el servicio generico `cloudflared` si existe y restaura:
  - `cloudflared-eXcom`.
  - `cloudflared-SaaS`.
- `cloudflared-SaaS` queda preparado con `--url http://localhost:5173`, aunque el diagnostico demuestra que el destino efectivo se gobierna por la configuracion remota del tunel.
- Se crea el tunel CLI-managed `giproy-network-classic` para independizar `giproy-network.excompc.dpdns.org` de la configuracion remota que no tenia ese hostname.
- Se agrega `CloudFlared-bkp/giproy-network-classic.yml` con ingress local:
  - `giproy-network.excompc.dpdns.org` hacia `http://localhost:5173`.
  - fallback `http_status:404`.
- Se enruta el DNS de `giproy-network.excompc.dpdns.org` al tunel `giproy-network-classic`.
- Se crea el servicio Windows `cloudflared-GiProyNetwork` con `AppDirectory` en el repo y `AppParameters` relativos para evitar fallos por el espacio en `GiProy Network`.

## Validacion

- `cloudflared-eXcom`: `RUNNING`.
- `cloudflared-SaaS`: `RUNNING`.
- `cloudflared-GiProyNetwork`: `RUNNING`.
- Tunel `giproy-network-classic`: conector activo.
- Procesos `cloudflared.exe` activos como servicios Windows.
- `http://127.0.0.1:5173`: HTTP 200.
- `https://giproy-network.excompc.dpdns.org`: HTTP 200.

## Causa raiz remota aislada

La configuracion remota de Cloudflare Zero Trust del tunel anterior no incluia el Public Hostname:

- Hostname: `giproy-network.excompc.dpdns.org`
- Tunnel: `giproy-erp-beta`
- Service: `http://localhost:5173`

La solucion aplicada evita depender de ese ingress remoto creando un tunel CLI-managed dedicado para el hostname publico clasico.
