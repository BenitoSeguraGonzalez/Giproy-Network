# TASK-1810 - Limpieza defensiva de contexto al cambiar empresa

Fecha: 2026-05-25

Modo: GIPROY CLASICO

## Objetivo

Evitar que un usuario `superadministrador` arrastre en frontend una base de trabajo o proyecto activo de una empresa anterior al cambiar de empresa operativa.

## Diagnostico

La base de datos local no muestra ruptura multi-tenant para `Administradores Generales`: solo existe una base de trabajo con `empresa_id=1`.

Las otras bases observadas pertenecen a `Santiago Bermeo` (`empresa_id=3`). El riesgo estaba en la rehidratacion/persistencia frontend de `selectedBaseTrabajo` o `activeProject` desde `localStorage`, que podia mantener visible una base activa de otra empresa aunque la lista principal ya consultara `bases-trabajo` con `empresa_id` correcto.

## Alcance

- Frontend clasico: `frontend/src/context/AuthContext.jsx`.
- Sin cambios de backend.
- Sin cambios de base de datos.
- Sin cambios de contratos API, rutas, auth, JWT ni permisos.
- Sin cambios en EDT, presupuestos, cronogramas ni datos.
- Sin cambios BIM, UX BIM ni acoplamientos hacia BIM.
- Sin Docker, Coolify, CI/CD, staging ni produccion.

## Cambios

- Se agrega una guarda defensiva en `AuthContext`.
- Si la empresa activa cambia y la base activa tiene `empresa_id` distinto, se limpia `selectedBaseTrabajo` y `giproy_working_base`.
- Si el proyecto activo tiene `empresa_id` distinto, se limpia `activeProject` y `giproy_working_project`.
- Se conserva la seleccion normal de empresa, base y proyecto cuando pertenecen al mismo tenant.

- `npm run build` OK desde `frontend/`.
