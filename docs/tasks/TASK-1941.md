# TASK-1941 - Motor comun de portabilidad clasica para Transferencias

Estado: cerrada
Fecha: 2026-06-17
Modo: GIPROY CLASICO

## Objetivo

Adecuar la importacion de proyectos recibidos por `Envios y Transferencias`
para que no duplique una rutina propia que rompa la relacion entre Proyecto,
Base de Proyecto, APUs y Presupuesto.

## Alcance

- Crear una capa comun de portabilidad clasica para copiar proyectos vivos entre
  empresas.
- Usar esa capa comun tambien desde Marketplace cuando entrega un Proyecto
  referenciado o de Compras Publicas ya materializado.
- Reutilizar el clonado profundo existente de `BaseTrabajo`.
- Construir el mapa `APU origen -> APU destino` desde `source_apu_id`.
- Clonar EDT y presupuestos conservando `PresupuestoDetalle.apu_id`.
- Exportar snapshot de Proyecto con Base de Proyecto, unidades, recursos y APUs
  para poder importar sin depender del proyecto origen vivo.
- Bloquear en preflight/importacion cualquier Proyecto sin Base de Proyecto,
  sin APUs o con lineas operativas de presupuesto sin `apu_id`.
- Validar que las lineas operativas del presupuesto importado apuntan a APUs de
  la base clonada de la empresa receptora.
- Corregir el clonado de unidades privadas en bases clonadas para no arrastrar
  unidades propias de otra empresa.
- Mantener fallback legacy para snapshots antiguos sin proyecto vivo.

## No alcance

- No se cambia BIM.
- No se cambian contratos publicos de API.
- No se modifican auth, JWT, permisos ni tenant.
- No se incorporan cronogramas, Gantt, documentos ni uploads a Transferencias.
- No se crean Dockerfiles, pipelines, Coolify, staging ni produccion.

## Cambios

- Nuevo servicio `backend/app/services/classic_asset_portability.py`.
- `transferencias.py` usa el motor comun cuando el envio referencia un proyecto
  vivo de la empresa emisora.
- `marketplace_checkout.py` delega la copia Proyecto/Base/APU/EDT/Presupuesto
  al mismo servicio comun y conserva sus extensiones especificas de contexto
  para detalle, EDO y cronogramas.
- `transferencias.py` embebe el catalogo tecnico de la Base de Proyecto en el
  snapshot de Proyecto.
- El preflight de Proyecto exige Base de Proyecto, APUs y lineas operativas de
  presupuesto enlazadas a APU; Datos + EDT + Presupuesto sin APU no es
  exportable.
- El fallback de importacion por snapshot reconstruye el mapa de APUs y evita
  crear lineas operativas con `apu_id=None`.
- `base_trabajo_repo.create` admite `commit=False` para uso atomico desde
  servicios superiores, conservando `commit=True` por defecto.
- `base_trabajo_repo._clone_deep_content` clona unidades no globales al contexto
  de la base/empresa destino.
- Se corrige referencia interna `new_base.id` inexistente en log de clonacion.

## Resultado

La importacion de un proyecto por Transferencias deja de crear presupuestos con
lineas operativas sin APU cuando el proyecto origen tiene Base/APUs validos. La
copia destino queda con Base de Proyecto propia, APUs clonados y presupuesto
enlazado al APU destino. El snapshot tambien contiene el catalogo necesario para
importar de forma inmutable si el proyecto origen ya no puede resolverse. Un
Proyecto sin Base de Proyecto/APUs queda bloqueado porque no cumple la ley
funcional del dominio clasico.
