# TASK-1953 - Snapshot inmutable en importacion de Proyectos transferidos

Fecha: 2026-06-18
Modo: GiProy Clasico
Estado: Cerrada

## Objetivo

Corregir y blindar `Envios y Transferencias` para que la importacion de un
Proyecto respete el snapshot exportado. Si el envio contiene Base de Proyecto y
APUs acotados, el receptor debe importar exactamente ese grafo y no recalcular
contra el Proyecto fuente vivo.

## Diagnostico

El caso local revisado mostro el envio `id=9` de `Test Apus Optimizado` con
preflight historico de 177 APUs en la Base de Proyecto. En el estado actual del
codigo, el snapshot del Proyecto `id=32` ya queda acotado correctamente a 5
APUs usados por el presupuesto, pero existia una brecha:

- `_import_project_payload` priorizaba clonado vivo cuando el Proyecto fuente
  seguia existiendo en la misma base de datos.
- Si el Proyecto fuente cambiaba despues de crear el envio, la importacion podia
  incorporar APUs posteriores que no estaban en el snapshot enviado.
- Eso rompia la idea de snapshot inmutable y podia volver a inflar la Base de
  Proyecto importada.

## Cambios realizados

- `backend/app/services/transferencias.py` ahora trata el payload moderno de
  Proyecto (`base_trabajo` o `apus`) como fuente de verdad de importacion.
- El clonado vivo con `classic_asset_portability_service` queda solo como
  fallback legacy para envios antiguos que no traen grafo Base/APU en el
  payload.
- Se agregaron guardas focales en
  `backend/app/tests/test_transferencias_import.py`:
  - Base de Proyecto con 177 APUs y presupuesto con 5 APUs enlazados.
  - Lineas operativas con `tipo=None`, como en datos reales.
  - Snapshot de Proyecto no exporta APUs no usados.
  - Importacion viva no clona la base completa.
  - Importacion respeta el snapshot aunque el Proyecto fuente cambie despues
    del envio.

## Impacto

Impacto acotado al backend clasico de `Envios y Transferencias`.

- No cambia contratos API visibles.
- No cambia rutas.
- No toca frontend.
- No toca DB ni migraciones.
- No cambia exportacion completa de `Base de Trabajo` cuando el usuario envia
  explicitamente una base.
- Mejora la consistencia de Proyectos transferidos: el envio importa el grafo
  exportado, no el estado vivo posterior.

## No interferencia

- Sin BIM, UX BIM ni dependencias BIM.
- Sin Docker/Coolify/CI/CD/staging/produccion.
- Sin cambios en auth, JWT, tenant global, permisos, EDT, presupuestos,
  cronogramas ni datos productivos.
- No se reabre TASK-1807 ni se eliminan guardas del baseline seguro.

## Rollback

Rollback focal posible:

- Revertir el cambio condicional en `backend/app/services/transferencias.py`.
- Revertir las guardas agregadas a
  `backend/app/tests/test_transferencias_import.py`.

El rollback devolveria la importacion de Proyecto al comportamiento previo:
usar clonado vivo cuando el Proyecto fuente exista, con riesgo de divergencia
frente al snapshot enviado.
