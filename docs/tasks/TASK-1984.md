# TASK-1984 - Politica transversal de precios, Gantt y modificaciones activas

Fecha: 2026-06-26

Modo: GIPROY CLASICO

## Objetivo

Documentar la politica enterprise que elimina la ambiguedad entre precios de
Base Proyecto, modificaciones activas, Presupuesto, Tanteos y Gantt. El
objetivo es que ningun modulo pueda mostrar, guardar o propagar un precio sin
declarar su origen funcional.

## Diagnostico

- Gantt puede calcular costos operativos ajustados por recursos, duracion,
  cantidades, rendimientos y APUs anidados explotados.
- Presupuesto y APUs usan la base funcional activa para calcular costo directo,
  indirectos y precio total.
- La regresion observada aparece cuando un valor operativo de Gantt se presenta
  como precio de presupuesto o precio oficial del APU.
- El problema no debe resolverse por empresa ni por pantalla; debe resolverse
  como politica transversal universal de la aplicacion.

## Politica confirmada

- La fuente de verdad es la base funcional activa:
  - modificacion activa si existe;
  - si no existe, Base Proyecto.
- Solo puede existir una modificacion activa por
  `empresa_id + proyecto_id + base_trabajo_id + revision_id`.
- Toda modificacion de precios vive dentro de `proyecto + revision`; no
  contamina otros proyectos que usen la misma base original.
- Una edicion normal de APU desde Presupuesto es global dentro del
  proyecto/revision activa.
- Gantt usa dos confirmaciones:
  - confirmar editor light: guarda borrador Gantt, solo afecta Gantt;
  - confirmar Gantt global: aplica al proyecto/revision y propaga al resto del
    sistema.
- Presupuesto, APUs, cronogramas y reportes ignoran borradores Gantt pendientes.
- Al aplicar Gantt global, el borrador se convierte en modificacion funcional
  activa y se recalculan APUs, Presupuesto, cronograma valorado, cronograma
  recursos y reportes.

## Opciones funcionales cerradas

### Ambito de modificacion activa

- La modificacion activa no es global a toda la base compartida; vive dentro de
  `empresa + proyecto + base_trabajo + revision`.
- La base de proyecto original queda como referencia estable.
- La modificacion activa se sobrepone a la base de proyecto solo cuando existe
  revision activa.
- Solo puede haber una modificacion activa vigente para el mismo alcance.

### Edicion desde Presupuesto

- Editar un APU desde la linea de Presupuesto modifica el APU funcional activo
  del proyecto/revision.
- El cambio es global para todas las apariciones de ese APU dentro del mismo
  proyecto/revision.
- No se permiten valores distintos del mismo APU por ocurrencia salvo que exista
  una regla funcional explicita futura.
- El editor de Presupuesto puede cambiar precio mediante recursos, APUs
  anidados, indirectos y tanteos aceptados.

### Edicion desde Gantt

- El editor light de Gantt no cambia la cantidad de la partida de Presupuesto.
- El editor light trabaja sobre recursos operativos, cantidad operativa,
  rendimiento y trabajo relativo.
- Confirmar dentro del editor light no propaga a Presupuesto; crea o actualiza
  borrador Gantt backend.
- Aplicar Gantt global es la unica accion que convierte esos cambios en fuente
  funcional activa para el resto del sistema.

### APUs anidados y explosion

- En Gantt, los APUs anidados se explotan y desaparecen como APUs hijos
  visibles en la capa operativa.
- Sus recursos se convierten en recursos funcionales del APU padre.
- Los recursos equivalentes se consolidan con sus pares del APU padre.
- El rendimiento consolidado se calcula con trabajo relativo:

```text
trabajo_relativo = cantidad * rendimiento
rendimiento_nuevo = trabajo_relativo_total / cantidad_total
```

- Si el APU tiene recursos explotados desde anidados:
  - el trabajo relativo queda fijo;
  - al cambiar cantidad se recalcula rendimiento;
  - el rendimiento no se edita como valor libre.
- Si el APU no tiene anidados:
  - cantidad y rendimiento son editables;
  - el trabajo relativo se recalcula.

### Visibilidad e indicadores

- Las filas Gantt con borrador pendiente deben tener indicador sutil de
  modificacion no propagada.
- Las filas con APUs anidados explotados deben mostrar indicador discreto de
  explosion/consolidacion.
- Las filas invalidadas deben verse como pendientes de resolucion, sin usar
  color de error para estados no criticos.
- En editor light, el color de `anidado` no debe ser rojo para evitar semantica
  de alarma.

### Confirmaciones y cancelaciones

- Cerrar o cancelar el editor light descarta cambios locales no confirmados.
- Confirmar el editor light guarda borrador Gantt, no modifica Presupuesto.
- Cancelar un borrador Gantt confirmado debe revertir solo el borrador, no la
  base funcional activa.
- Aplicar globalmente Gantt ejecuta preflight y propaga si no hay incidencias.
- Si existen lineas invalidadas, el usuario debe descartarlas o ajustarlas antes
  de aplicar globalmente.

### Concurrencia

- Varios usuarios pueden ver un mismo Gantt.
- Solo un usuario puede editarlo a la vez.
- El bloqueo de edicion es por `proyecto + revision + cronograma`.
- Si otro usuario intenta editar, ve el Gantt en modo lectura, con informacion
  del usuario que posee el lock.
- Puede solicitar liberacion mediante notificaciones.
- Al liberarse el Gantt, el solicitante debe ser avisado.

### Informes

- Los informes oficiales nunca incluyen borradores ni tanteos pendientes.
- Si existen pendientes, el informe debe declararlo como advertencia.
- Los pendientes no son trabajos terminados y no participan en totales
  oficiales.

## Gantt, borradores y tanteo operativo

- El editor light de Gantt puede trabajar como tanteo local.
- Al abrir el editor se crea una copia aislada:
  - snapshot inicial oficial;
  - draft local editable.
- Cerrar con `X` o cancelar descarta el draft local.
- Confirmar el editor light guarda el cambio como borrador Gantt backend.
- Los cambios confirmados en editor light, pero no aplicados globalmente, deben
  persistir como borrador para retomar el trabajo en diferentes sesiones.
- El borrador Gantt es unico por `proyecto + revision + cronograma`.
- Los cambios no confirmados ni siquiera en editor light son locales y se
  descartan si se cierra, expira el lock o se abandona la sesion.

## Regla de APUs anidados

- Si el APU tiene APUs anidados explotados:
  - el trabajo relativo permanece fijo;
  - el usuario puede cambiar cantidad;
  - el rendimiento se calcula automaticamente;
  - el rendimiento no debe actuar como entrada manual principal.
- Si el APU no tiene anidados:
  - el usuario puede cambiar cantidad;
  - el usuario puede cambiar rendimiento;
  - el trabajo relativo se recalcula.
- Esta logica vive dentro del editor mientras no se confirme.
- Solo al confirmar globalmente Gantt se propaga al resto del sistema.

## Intencion operativa y snapshot

Todo cambio aceptado debe registrar dos capas:

- intencion estructurada:
  - que quiso cambiar el usuario;
  - sobre que recurso/APU/linea;
  - con que entrada operativa.
- snapshot recalculado:
  - resultado oficial despues de aplicar la intencion;
  - costo directo;
  - indirectos;
  - precio total;
  - recursos y rendimientos efectivos.

La regeneracion nunca debe reutilizar importes derivados antiguos. Debe hacer:

```text
nueva_base_activa + intencion_operativa -> nuevos derivados
```

## Identidad de recursos

No se debe reconocer un recurso solo por `recurso_id`. La identidad debe ser
compuesta, especialmente para APUs anidados y recursos consolidados:

- tipo de origen: directo, anidado, consolidado, consolidado mixto;
- `recurso_id`;
- codigo;
- unidad;
- categoria normalizada;
- `apu_origen_id` cuando aplique;
- `apu_hijo_id` cuando aplique;
- path de anidacion cuando aplique.

En editor light, una fila consolidada se edita como consolidado completo. Si se
requiere edicion por origen individual, debe ser otro flujo explicito.

## Precedencia entre modulos

- Presupuesto oficial prevalece sobre borradores Gantt pendientes relacionados.
- Si Presupuesto modifica una linea/APU/recurso que afecta un borrador Gantt,
  solo se invalidan las partes relacionadas, no todo el borrador.
- Los cambios invalidados:
  - quedan visibles como invalidados;
  - no participan en calculos;
  - no pueden aplicarse en estado antiguo;
  - deben descartarse o ajustarse desde la base activa.
- Ajustar significa conservar solo la intencion operativa compatible y
  recalcular contra la nueva base activa.
- Tanteos y borradores Gantt pueden coexistir como escenarios, pero la primera
  confirmacion oficial invalida escenarios pendientes relacionados.

## Confirmacion global de Gantt

Al aplicar Gantt global se ejecuta un preflight automatico. Si falla, no aplica
y debe explicar incidencia y motivo.

Validaciones minimas:

- lock de edicion Gantt pertenece al usuario;
- permisos suficientes para aplicar globalmente;
- estado del proyecto permite modificaciones;
- borrador activo pertenece a la misma empresa/proyecto/revision/cronograma;
- no hay lineas invalidadas sin resolver;
- no hay modificaciones oficiales posteriores no reconciliadas;
- APUs sin ciclos y sin referencias rotas;
- recursos consolidados resolubles;
- cantidades y rendimientos validos;
- formulas de anidados y no anidados respetadas;
- snapshot oficial recalculado antes de persistir;
- auditoria completa.

Si hay lineas invalidadas, el sistema abre resolucion obligatoria:

- descartar invalidada;
- ajustar/regenerar desde base activa.

Solo despues de resolver se permite aplicar globalmente.

## Locks y sesiones Gantt

- Varios usuarios pueden ver el mismo Gantt si tienen permisos.
- Solo un usuario puede trabajar/editar Gantt a la vez.
- La edicion requiere lock exclusivo por proyecto/revision/cronograma.
- Si otro usuario intenta editar:
  - entra en solo lectura;
  - ve quien esta usando Gantt;
  - puede solicitar liberacion mediante notificaciones.
- El lock usa heartbeat y expiracion controlada.
- Si expira el lock, el borrador backend no se borra.
- Un usuario con permisos puede reclamar un lock expirado.
- Liberaciones, expiraciones y reclamos quedan auditados.

## Estados de proyecto

- Borrador / En planificacion:
  - permite edicion de Presupuesto;
  - permite tanteos;
  - permite borrador Gantt;
  - permite aplicar Gantt global.
- Aprobado / Contratado:
  - permite cambios solo mediante permiso superior o revision/modificacion
    autorizada.
- En ejecucion:
  - permite cambios controlados segun politica del proyecto.
- Cerrado / Archivado:
  - solo lectura;
  - no permite nuevos borradores ni aplicar pendientes.

Cuando el proyecto cambia de estado general:

- se cancelan borradores Gantt pendientes;
- se cancelan tanteos pendientes;
- se cancelan ediciones no aplicadas;
- se conserva auditoria;
- se debe advertir al usuario antes de la transicion.

## Reportes y exportaciones

- Reportes oficiales solo usan la fuente funcional activa.
- No incluyen borradores Gantt pendientes.
- No incluyen tanteos pendientes.
- No incluyen lineas invalidadas.
- Deben advertir si existen trabajos pendientes no aplicados.

Ejemplo:

```text
Este proyecto/revision contiene cambios Gantt pendientes y tanteos abiertos no
incluidos en este informe.
```

## Reversion

Una modificacion activa aplicada puede revertirse solo mediante nueva
modificacion auditada:

- no se borra historia;
- se crea una nueva version activa basada en snapshot anterior;
- se recalculan consumidores;
- se invalidan pendientes relacionados;
- se registra usuario, fecha y motivo.

## Saneamiento de datos actuales

El saneamiento debe ser universal y conservador:

- auditar cronogramas existentes;
- detectar metadata ambigua;
- clasificar casos consistentes, recalculables y de revision manual;
- recalcular solo si es deterministico;
- conservar snapshot anterior;
- nunca tocar precios oficiales sin trazabilidad.
