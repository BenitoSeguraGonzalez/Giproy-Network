# TASK-2001 - Docker beta automatizable para servidor clasico

## Contexto

El usuario autoriza abrir la Fase 6 para estudiar el servidor
`192.168.18.106` y preparar una estructura Docker repetible para desplegar la
beta actual de GiProy Clasico.

El servidor observado:

- Ubuntu 24.04.4 LTS.
- 12 cores, 7.6 GiB RAM y 81 GiB libres en `/`.
- Docker 29.6.0 y Docker Compose v5.2.0.
- Redes Docker existentes: `proxy` y `backend`.
- Traefik v2.11 activo en `127.0.0.1:80`.
- Cloudflared activo con wildcard `*.excomconsultores.com` hacia Traefik.
- PostgreSQL systemd instalado pero cluster local `16/main` apagado.
- `~/docker/apps` existe y esta libre para aplicaciones.

## Alcance

- Crear artefactos Docker para GiProy Clasico beta.
- Crear scripts de preflight, backup y despliegue repetible.
- Mantener despliegue aislado bajo `~/docker/apps/giproy-beta`, con el repo o
  paquete completo como raiz y los controles en `deploy/`.
- Usar la base local actual como semilla inicial de datos del servidor beta.
- No modificar contratos API, auth, tenant, presupuestos, cronogramas ni BIM.
- No ejecutar cambios destructivos en PostgreSQL.

## Cambios

- Se crea `.dockerignore` conservador para excluir secretos, dumps, backups,
  logs, uploads, runtime local, venvs, `node_modules` y artefactos pesados.
- Se crea `backend/Dockerfile` para FastAPI/Gunicorn sobre Python 3.12 slim.
- Se crea `frontend/Dockerfile` multi-stage para Vite + Nginx.
- Se crea `frontend/nginx.conf` con proxy interno `/api` y `/uploads` hacia el
  backend.
- Se crea `deploy/docker-compose.beta.yml` con servicios `postgres`, `migrate`,
  `backend` y `frontend`, usando redes externas `proxy` y `backend`.
- El PostgreSQL beta se alinea a `postgres:18` porque la base local fuente corre
  PostgreSQL 18.4.
- Para `postgres:18`, el volumen se monta en `/var/lib/postgresql` siguiendo la
  convencion nueva de la imagen oficial.
- Se crea `deploy/env/giproy-beta.env.example` sin secretos reales.
- Se crean scripts:
  - `deploy/scripts/giproy-beta-preflight.sh`
  - `deploy/scripts/giproy-beta-backup.sh`
  - `deploy/scripts/giproy-beta-deploy.sh`
  - `deploy/scripts/giproy-beta-import-seed.sh`
- Se documenta el flujo en `deploy/README.md`.
- Se corrige `@react-leaflet/core` de `2.1.1` a `2.1.0` porque `2.1.1` no
  existe en npm y bloqueaba `npm ci` durante el build Docker.

## Seguridad

- El script legado `setup_server.sh` queda descartado para este frente porque
  contiene pasos destructivos (`DROP DATABASE`, `DROP USER`) y creacion de
  esquema desde modelos.
- El nuevo flujo usa volumen dedicado y `pg_dump` previo si la DB del compose ya
  existe.
- Las migraciones Alembic se ejecutan por servicio `migrate` controlado por el
  script de despliegue, no dentro del arranque normal del backend.
- El repo tiene multiples heads Alembic, por lo que Docker beta usa
  `alembic upgrade heads` en vez de `head`.
- Como la revision inicial Alembic es baseline y no crea todo el esquema, el
  deploy detecta DB vacia, ejecuta un bootstrap controlado desde modelos y luego
  aplica `alembic stamp heads`. En DB no vacias usa migraciones Alembic.
- Tras aclaracion del usuario, el cierre correcto no es DB vacia sino importar
  un `pg_dump` local como datos iniciales del servidor.
- `CREATE_TABLES_ON_STARTUP=false` y `BIM_ENABLED=false` quedan forzados por
  compose.
