# TASK-2011 - Optimizacion de carga Gantt clasico en servidor

Fecha: 2026-07-08

Modo: GIPROY CLASICO

## Objetivo

Reducir el cuello de botella de carga de Gantt clasico en
`giproy.excomconsultores.com`, manteniendo contratos por defecto, datos, auth,
tenant y BIM sin cambios.

## Diagnostico

- El usuario reporta que Gantt tarda cerca de 30 s y Presupuesto tambien se
  percibe lento.
- En el caso documentado `presupuesto_id=29`, el calculo interno de Gantt no
  explicaba por si solo los 30 s:
  - Servidor antes de optimizar payload: `_build_response` ~2,24-2,47 s.
  - HTTP publico antes: `GET /cronogramas-trabajo/29` devolvia ~10,46 MB y
    tardaba ~6,46-18,27 s.
  - `GET /cronogramas/valorados/29` tardaba ~4,90-5,44 s.
  - `GET /cronogramas-trabajo/29/gantt-draft` tardaba ~2,47-2,76 s.
- El payload tenia duplicacion pesada:
  - `rows`: ~6,43 MB.
  - `schedule_data`: ~4,78 MB.
  - `rows.metadata`: ~6,07 MB, con metadatos usados por el editor Gantt.
- El perfil local tambien mostro costo CPU repetido en calendario laboral:
  `_is_workday`, `_resolve_workday_day_start`, `_align_to_workday_start` y
  `_uses_advanced_calendar`.

## Cambios realizados

- `backend/app/services/cronograma_trabajo.py`:
  - Se agrega `_WORKDAY_CALC_CACHE` contextual por construccion de respuesta.
  - `_build_response(...)` inicializa y limpia ese cache junto al cache de
    overrides existente.
  - Se cachean resultados de `_uses_advanced_calendar(...)`,
    `_is_workday(...)`, `_resolve_workday_day_start(...)` y
    `_align_to_workday_start(...)`.
  - Se normaliza defensivamente `presupuesto.revision`.
  - Se evita iterar `presupuesto.detalle` si el atributo no es iterable.
- `backend/app/main.py`:
  - Se habilita `GZipMiddleware` para respuestas HTTP mayores a 1024 bytes.
- `backend/app/api/endpoints/cronogramas_trabajo.py`:
  - Se agrega `compact: bool = Query(False)` en `GET
    /cronogramas-trabajo/{presupuesto_id}`.
  - Por defecto el contrato sigue completo.
  - Con `compact=true`, la respuesta conserva `rows` y devuelve
    `schedule_data={}` para evitar duplicacion en la carga inicial.
- `frontend/src/api/cronogramas.js`:
  - `getTrabajo(...)` acepta `options.compact`.
- `frontend/src/components/projects/Cronogramas.jsx`:
  - La carga clasica de Gantt pide `compact=true`.

## Medicion

- Local antes:
  - `_build_response` presupuesto `29`: ~2,38 s.
- Local despues de cache calendario:
  - `_build_response` presupuesto `29`: ~1,21-1,75 s.
  - 224 filas, `bad_dates=0`.
- Servidor antes de `compact/gzip`:
  - `GET /cronogramas-trabajo/29`: ~6,46-18,27 s, ~10,46 MB.
- Servidor despues:
  - Respuesta completa compatible:
    - ~3,68-3,79 s.
    - `Content-Encoding: gzip`.
    - `Content-Length`: ~556 KB comprimidos.
  - Respuesta compacta usada por frontend:
    - ~3,02-3,76 s.
    - ~6,03 MB decodificados.
    - `Content-Length`: ~364 KB comprimidos.
    - `schedule_data_len=0`, `rows=224`.
  - Waterfall HTTP autenticado equivalente a carga de Cronogramas:
    - ~8,18-8,71 s total.
